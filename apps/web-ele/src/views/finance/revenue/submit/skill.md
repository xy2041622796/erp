# 收款提报页面 skill

## 页面入口
- 路径：`apps/web-ele/src/views/erp/finance/revenue/submit`
- 页面文件：`index.vue`
- 弹窗表单：`modules/form.vue`
- 配置文件：`data.ts`

## 页面能力
- 支持新增、编辑、查看收款提报。
- 支持从收入结算列表直接打开“新增收款提报”弹窗。
- 支持在弹窗内选择业务单据，也支持由收入结算页面预带业务单据。
- 支持按状态查看全部 / 待审批 / 待确认 / 已确认。
- 列表页支持审批流按钮：
  - `status=0` 显示“审批”，点击后流转到 `status=1`；
  - `status=1` 显示“反审批”和“确认”；
  - `status=2` 不显示审批类按钮。

## 预带规则
- 当由收入结算页面以“生成提报单”方式打开时，弹窗支持接收：
  - `presetValues`：预填主表字段（客户、项目、合同等）；
  - `presetSettlements`：预填业务单据子表。
- 弹窗打开后会自动：
  - 回显所带收入结算单；
  - 自动计算本次核销合计并回写到账金额；
  - 按所带单据自动回填客户、项目、合同。

## 使用到的数据与接口
- 收款提报主接口：`#/api/erp/finance/revenue/submit`
- 收入结算接口：`#/api/erp/finance/revenue/settlement`
- 核销关联接口：`#/api/erp/finance/revenue/writeoff`
- 项目接口：`#/api/erp/finance/revenue/settlement/project`
- 客户/员工/部门选择：
  - `#/api/erp/customer`
  - `#/api/system/user`
  - `#/api/common/staff-selector`

## 收入结算状态联动
- 新增收款提报成功后，会把当前提报关联到的收入结算单状态统一更新为 `30=已完成`。
- 该逻辑放在收款提报弹窗保存成功后统一执行，因此同时覆盖两条入口：
  - 收入结算页面“生成提报单”；
  - 收款提报页面直接新增并选择业务单据。

## 收款账户下拉
- 收款提报表单中的 `收款账户` 已改为账户下拉选择。
- 下拉数据来源：`#/api/erp/finance/account` 的 `getAccountSimpleList`。
- 表单保存值为账户主键 `rowid`。

## 预带收款账户
- 从收入结算页面点击“生成提报单”打开新增收款提报时，会将收入结算中的 `receive_account` 预带到收款提报的 `collection_account`。

## 多次提报与确认
- 同一张收入结算单可被多次收款提报关联。
- 新增收款提报时，“本次核销”默认带出当前结算单的 `receive_balance`（可申请余额）。
- 提报创建成功后，仅将关联收入结算单推进到 `25=收款中`，不会立即减少余额。
- 当提报单在列表中被“确认”后，系统才会：
  - 累加收入结算单的 `receive_amount`；
  - 扣减收入结算单的 `receive_balance`；
  - 根据余额判断收入结算单状态为 `25=收款中` 或 `30=已完成`。

## 创建与确认分离
- 新增收款提报保存成功后，只会将关联收入结算单状态推进到 `25=收款中`。
- 收款提报列表中的“确认”按钮才会真正更新收入结算的 `receive_amount`、`receive_balance` 与状态。
- 已确认单据不再显示审批类按钮。

## 本次核销输入同步
- 收款提报弹窗中的“本次核销”不再只绑定表格行临时对象，而是显式同步回 `selectedSettlements`。
- 保存提报时，核销关联表 `Bil_Submit_WriteOff` 使用用户实际输入的 `apply_amount` 写入 `write_off_amount`。

## description 规范化
- 新增/编辑收款提报时，`description` 不再写入业务单据 JSON 快照。
- 新数据仅写入纯文本摘要（如“关联3条业务单据”），避免列表展示 JSON 文本。
- 提报与收入结算的正式关联数据仍以 `Bil_Submit_WriteOff` 为准。
- 详情/编辑时继续保留对历史 `description.items` 的兜底兼容，避免旧单据回显异常。

## 收入结算确认回写口径
- 收款提报确认时，仅回写收入结算的 `receive_amount`、`receive_balance` 与 `status`。
- 不再在确认时联动更新 `ticket_amount`，避免误伤开票金额口径。

## 确认幂等处理
- 收款提报确认时，仅处理 `write_off_status != 1` 的核销关联记录。
- 回写收入结算成功后，再将对应关联记录标记为 `write_off_status=1`，避免重复确认重复扣减。

## 删除提报时级联删除核销子表
- 收款提报删除时，会同时逻辑删除 `Bil_Submit_WriteOff` 中该提报对应的核销关联记录。
- 避免出现主表删除后，核销子表残留的问题。

## 核销关联查询容错
- 收款提报确认时，核销关联查询改为优先按 `submit_id` 查询，再在前端优先收敛到目标 `write_off_type`。
- 若历史数据的 `write_off_type` 为空或异常，也不会因为过滤过严导致整张提报查不到核销关联。

## 业财维度联动
- 收款提报在外层列表页执行“确认”时，才会根据收款账户/收款类型自动解析借贷科目并生成维度。
- 新增、编辑保存时不生成业务维度，只保留提报主表与核销关联的保存。
- 系统会把本次业务转换为财务的结果写入业务维度表：
  - `Bil_Dimension_Set`：写入事件 `COLLECTION_SUBMIT_CONFIRM`、业务分类 `收款`、业务单号与业务日期；
  - `Bil_Dimension_Detail`：写入借方科目、贷方科目，以及部门、客户、业务单号等业务维度；
  - 同时新增一条业务维度 `BIZ_TO_FINANCE`，写入“借:xxx / 贷:xxx”的业财转换内容，便于台账追溯。
- 同一张收款提报重复确认时，会先软删除旧维度，再重建当前维度，避免重复数据。

## 收款提报维度同步
- 收款提报保存成功后，会按 `COLLECTION_SUBMIT` 事件写入财务维度台账。
- 维度主表分类为 `biz_category=收款`，业务单号优先使用 `ReportID`，兜底使用 `rowid`。
- 财务维度会落两条科目映射：
  - 借方：根据收款账户识别为 `1001=库存现金` 或 `1002=银行存款`；
  - 贷方：根据业务类型识别为 `1122=应收账款` 或 `2203=预收账款/合同负债`。
- 业务维度新增 `BIZ_TO_FINANCE`，用于记录“业务类型 -> 财务科目”的转换内容，同时补充 `CUSTOMER`、`PROJECT`、`CONTRACT` 等业务维度。
- 同一张提报再次编辑保存时，会先软删除旧维度，再按最新数据重建，避免重复脏数据。

## 确认流程回退
- 收款提报“确认”流程当前仅执行收入结算回写、核销关联状态更新与提报状态更新。
- 本次已移除确认时自动生成财务凭证的接入逻辑，避免凭证链路异常阻断确认主流程。
- 后续如需重做凭证联动，应以“不阻断确认主流程”为前提重新设计。
